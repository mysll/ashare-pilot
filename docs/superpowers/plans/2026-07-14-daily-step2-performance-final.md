# Daily Step 2 Performance Optimization — Final Development Plan

**Date:** 2026-07-14

**Status:** Final / Ready for implementation

**Scope:** `daily-market-analysis` Step 2 performance and correctness, plus the
minimal Step 3 contract needed to generate final-stock `source_basis` text.

**Supersedes:**

- `2026-07-14-step2-llm-annotation-reduction.md`
- `2026-07-14-daily-step2-performance-optimization.md`

---

## 1. Goal

Reduce daily Step 2 wall time from the observed 8–10 minutes while preserving
the information used by Step 3 to make trading decisions.

The optimization must preserve:

- complete Candidate Pool membership;
- deterministic theme membership, rank, and heat;
- candidate-specific `news_relevance` and `news_impact`;
- `major_event`, candidate `anomaly`, Pattern, risk, and strategy inputs;
- `role_tags` derived from actual Theme Library, market, news, and LHB sources;
- canonical `news#<id>` evidence references;
- JSON-first machine contracts.

The optimization must not:

- change composite weights;
- move Direction or RiskSeverity into Step 2;
- blanket-fill R2/P2;
- invent auction data or source flags;
- tighten universe top-N before measuring the LLM reductions;
- add concurrency to `fetch_pool_indicators.py`;
- retain a compatibility path for deleted theme-stock annotations;
- regenerate historical strategies.

---

## 2. Locked Decisions

These decisions are final for implementation.

1. `theme_stocks.json` owns final stock membership and `filter.status`.
2. `themes.json` owns theme membership, rank, heat, direction, and theme
   evidence.
3. `mapper.annotations.json` may enrich candidates but may not create or remove
   themes or stocks.
4. `theme_stocks.annotations.json` is deleted from the future workflow.
5. There is no legacy reader, override file, feature flag, or historical
   regeneration path for `theme_stocks.annotations.json`.
6. Theme Library / market / news / LHB source flags are generated by scripts
   from actual structured inputs before `theme_stocks.json` is published.
7. Candidate anomaly has one owner: `mapper.annotations.json`.
8. Observation anomaly has one owner: deterministic observation construction;
   no LLM theme-stock annotation path remains.
9. Intermediate files do not contain translated source prose or
   `source_explanation`.
10. Step 3 generates `reasoning.source_basis` for every stock actually emitted
    in `strategy.json.stocks[]`. The count is regime-dependent and is not always
    10.
11. `fetch_pool_indicators.py` remains sequential because concurrent requests
    may cause API rate limiting, IP blocking, or account risk.
12. Compact LLM input files are intermediate/non-contract artifacts. The plan
    does not introduce another long-lived formal sidecar contract.

## 3. Measured Baseline

### 3.1 2026-07-14 Step 2

From the completion of `news.json` to `mapper.strategy_view.json`, Step 2 took
approximately 495 seconds / 8 minutes 15 seconds.

| Stage | Approx. duration | Finding |
|---|---:|---|
| LLM writes `themes.json` | 186s | Primary bottleneck |
| Extra/universe/indicators/base | 36s | Indicator fetch about 18s |
| LLM writes `theme_stocks.annotations.json` | 129s | Entire removable LLM stage |
| Theme-stock validate/merge | 8s | Python itself is under 0.2s |
| LLM writes `mapper.annotations.json` | 119s | Primary bottleneck |
| Mapper build/validate/view | 18s | Mostly tool-call round trips |
| **Total** | **495s** | |

The three LLM authoring stages account for about 434 seconds, approximately
88% of Step 2.

### 3.2 Local Python cost

Using frozen 2026-07-14 inputs and temporary outputs, individual local
validators/builders took approximately 0.07–0.20 seconds. Eleven local commands
took about 1.2 seconds of actual Python runtime.

JSON parsing and merge computation are not the main regression. The main
causes are:

- three serial LLM-authored artifacts;
- large and duplicated context;
- verbose repeated annotation objects;
- many separate agent/tool round trips.

### 3.3 Repetitive annotation evidence

For 45 mapper annotations on 2026-07-14:

- 44/45 `major_event` values were `none`;
- 45/45 `pattern.auction` values were `NEUTRAL`;
- every stock contained five Pattern objects;
- volume was 34 `SURGE` and 11 `NORMAL`, derivable from numeric input;
- every theme-stock annotation contained `source_explanation`.

This is output-token work rather than useful semantic work.

## 5. Ownership Model

### 5.1 Theme ownership

| Information | Owner |
|---|---|
| Theme membership | `themes.json` |
| Rank | `themes.json` |
| Heat | `themes.json` |
| Direction | `themes.json` |
| Theme evidence | `themes.json` with `news#id` |
| Mapper dominant themes | Projected by Python from `themes.json` |

`mapper.annotations.json.themes[]` must not seed, create, remove, or reorder
themes. Prefer removing the duplicate theme annotation list entirely. If any
theme semantic overlay remains temporarily during implementation, it may only
overlay fields on an existing theme name.

### 5.2 Stock membership ownership

| Information | Owner |
|---|---|
| Universe membership | Theme Library + structured extras + scope scripts |
| Candidate/observation/removed | `theme_stocks.json.filter.status` |
| Candidate Pool membership | Python projection from `theme_stocks.json` |
| Candidate semantics | `mapper.annotations.json` |

No missing mapper annotation may remove an eligible candidate.

### 5.3 Source ownership

| Role tag | Deterministic source |
|---|---|
| `ThemeLibrary` | Theme Library candidate/pure/leader membership |
| `MarketActive` | selected-theme market view rules |
| `NewsDirect` | canonical news stock-name/code match or structured extra |
| `LHB` | structured LHB result |
| `MultiTheme` | multiple `source_themes` |
| `Anchor` | Theme Library anchor metadata |

No natural-language source trace is stored in intermediate contracts.

### 5.4 Anomaly ownership

- Candidate anomaly: `mapper.annotations.json` only.
- Observation anomaly: deterministic from observation/filter/risk inputs.
- Human-readable final selection basis: Step 3 only.

**Priority:** Blocking correctness prerequisite

**Files:**

### 6.1 Stock membership refactor

Replace annotation-driven candidate creation with deterministic construction:

```text
for stock in theme_stocks.json.stocks:
    if stock.filter.status == candidate:
        create mapper.base candidate
```

Then overlay `mapper.annotations.json` by code.

Required behavior:

- missing candidate annotation: candidate remains in mapper base;
- validation fails before mapper publication;
- observation annotation cannot promote a stock;
- extra legal annotation warns and skips;
- annotation order cannot change candidate membership or deterministic order.

### 6.2 Theme ownership refactor

Replace:

```text
mapper.annotations.themes → mapper.base themes / dominant themes
```

with:

```text
themes.json or theme_stocks.json.themes
    → mapper.base themes
    → market_state.dominant_themes
```

Theme membership, rank, and heat must not depend on mapper annotations.

### 6.3 Acceptance

```text
set(mapper.base.candidate_pool.code)
==
set(theme_stocks.json stocks where filter.status == candidate)
```

And:

```text
mapper.base.themes name/rank/heat
==
themes.json tradeable theme name/rank/heat
```

## 8. Task 2 — Delete `theme_stocks.annotations.json`

**Priority:** Highest performance win after Task 0

**Files:**

- Modify: `.opencode/skills/daily-stock-mapping/scripts/build_theme_stocks_universe.py`
- Modify: `.opencode/skills/daily-stock-mapping/scripts/build_theme_stocks_base.py`

- Modify: `.opencode/skills/daily-stock-mapping/scripts/mapper_json_lib.py`
- Delete: `.opencode/skills/daily-stock-mapping/scripts/validate_theme_stocks_annotations.py`
- Modify: `.opencode/skills/daily-stock-mapping/SKILL.md`
- Modify: `.opencode/skills/daily-market-analysis/SKILL.md`
- Add source-flag and deletion-equivalence tests

### 8.1 Mandatory source flag generation

Before publishing `theme_stocks.json`, prepare must build source flags from
actual structured data.

#### Theme Library

Generate `candidate=true` from selected-theme Theme Library membership.

#### Market view

Batch selected-theme market views and apply the existing rules:

- top-N `cross_rank_highlights` membership;
- full selected-theme `threshold_attention` where `attention_score >= 80`;
- full selected-theme `threshold_gainers` where `change_pct >= 3%`.

The display top-N parameter may limit cross-rank presentation, but it must not
truncate either threshold set.

Only qualifying records produce `market=true`.

#### News direct

Generate `news=true` only when a canonical same-day news item directly names
the stock by code/name, or when an accepted structured extra contains a valid
`news#id`.

#### LHB

Generate `lhb=true` only from a structured LHB record in scope for the day.

If a source is unavailable, keep its flag false. Do not infer or guess a flag.
Historical blanket-filled source tags must not be reproduced without evidence.
Any resulting source correction requires a dated, exact audit allowlist and a
passing Step 3 shadow; it is not a general role-tag waiver.

### 8.2 Field removal

Delete without replacement:

- theme annotation `note` / duplicate `evidence`;
- stock `source_explanation`;
- stock annotation `note`;
- candidate anomaly in this stage;
- annotation schema/version metadata.

Do not add `source_trace`, translated trace text, or a replacement annotation
sidecar.

### 8.3 Builder simplification

`build_theme_stocks_json.py` must:

- read `theme_stocks.base.json` only;
- publish `daily_theme_stocks.v1` directly;
- update generated metadata;
- use a deterministic generation mode.

Remove:

- `--annotations`;
- annotations file checks;
- annotations schema checks;
- `merge_theme_stock_annotations()`;
- `annotation_schema_version`;
- the annotation validator and all workflow references.

### 8.4 Observation anomaly

The current strategy view and HTML renderer expose observation anomaly, but
Step 3's candidate reasoning reads candidate anomaly. Preserve report behavior
through a single deterministic owner derived from observation `filter.reason`
and technical `risk_flags`. Do not introduce an observation LLM annotation
path.

### 8.5 Task 2 strict deletion gate

Task 2 is an intermediate deletion-only checkpoint. Before applying later
Pattern or sparse-annotation changes, old and new Step 3 decision inputs must
be equal.

Strict equality fields:

- `market_state`;
- themes name/rank/heat;
- candidate code set and order;
- candidate `role_tags`;
- all candidate scores;
- major events and risk types;
- Pattern;
- candidate anomaly;
- news link;
- strategy inputs;
- observation/excluded code sets and reasons.

Allowed differences at Task 2:

- generated timestamps;
- generation-mode/source metadata;
- deterministic observation anomaly wording only when candidate decisions and
  observation membership/reason are unchanged and the display diff is recorded.

No unexplained role-tag difference is allowed. An exact dated allowlist may
record removal of a historically blanket-filled tag only when the structured
source is absent and Gate D confirms unchanged selected names/order/directions.

### 8.6 Expected gain

Approximately 30–130 seconds per run, with about 129 seconds observed on
2026-07-14.

**Files:**

## 11. Task 5 — Sparse, Candidate-Complete Mapper Annotations

**Files:**

### 11.1 Required for every candidate

- `code`;
- complete candidate-specific `news_relevance` decision;
- confidence;
- canonical evidence or concise trace.

Every deterministic candidate code must appear exactly once.

### 11.2 Sparse optional fields

- `major_event` only for a named company-level discrete event;
- `anomaly` only for a mandatory trigger or genuine structural anomaly;
- `pattern` only for dimensions that override mapper-base defaults;
- `news_link` may be projected from `news_relevance.evidence`.

- `major_event.polarity=none` with deterministic trace;

- extra non-candidate annotations warn and skip at merge;
- suspicious blanket R2/P2 assignment fails review;
- missing optional fields are allowed only when mapper base owns the default.

Do not require repetitive prose such as “no company-specific event” for every
candidate.

## 20. Final Expected Result

The final daily path has two LLM semantic stages:

1. theme selection/heat;
2. candidate-complete sparse mapper semantics.

Python owns:

- theme and stock membership;
- filters and technical values;
- structured source flags and role tags;
- default Pattern and event values;
- mapper assembly, validation, and projection.

Step 3 owns:

- Direction and RiskSeverity;
- final strategy selection;
- readable `reasoning.source_basis` for every selected stock.

The removed `theme_stocks.annotations.json` stage no longer consumes LLM time,
and its only decision-visible effects are replaced before deletion by
deterministic, testable inputs.
