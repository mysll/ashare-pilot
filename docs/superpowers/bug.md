当前存在两个会直接让系统"打不出货"的硬
  bug,以及若干策略逻辑上的隐患。下面按严重程度说。

  🔴 一、致命:VWAP 取错字段,导致质量过滤器几乎全灭

  这是最严重的问题。enrich_compute_pool.py:70 把"分时均价线(VWAP)"取成了 5 分钟 K 线的 ma_price5:

  vwap = last.get("ma_price5")   # 这是"5根5分钟K线收盘价的均线",不是当日成交均价

  - ma_price5 是 MA5(5×5min=25 分钟均线),根本不是 VWAP(当日累计成交额/成交量)。
  - 实证:2026-07-01 那次,120 只票里 79 只 vwap==当日最高价、81 只 vwap==现价。因为尾盘拉升时,最近 25
  分钟均价≈现价≈最高价。
  - 后果:质量过滤器的第一条 price > vwap 形同虚设或反向误伤。

  修复:VWAP 应从实时快照直接算 amount / volume(成交额/成交量),East Money/Sina 的实时行情里都有 amount 和 volume。样本里
  real_time 已经带了这两个字段,直接算即可,根本不需要再单独发一轮 K 线请求(还能省掉 fetch_vwap_for_codes 的 120
  次并发调用)。

  🔴 二、致命:质量过滤器与选股目标自相矛盾,把票全过滤空了

  那次运行 120 只候选 → 0 只入池,opportunity_pool 完全为空,LLM
  只能写"全部观望"。根因是过滤器(score_overnight.py:246)和上游建池目标打架:

  ┌───────────────────────────────┬─────────────────────┬──────────────────────────────────────────────────┐
  │             环节              │      涨幅口径       │                       冲突                       │
  ├───────────────────────────────┼─────────────────────┼──────────────────────────────────────────────────┤
  │ build_scan_pool 抓 gain_range │ 2%~9%               │ 上游放进来大量 6%~9% 的票                        │
  ├───────────────────────────────┼─────────────────────┼──────────────────────────────────────────────────┤
  │ build_scan_pool 抓 limit_up   │ 涨停(~10%/20%)      │ 涨停票是 QuickScore 最高优先级(market_align=1.0) │
  ├───────────────────────────────┼─────────────────────┼──────────────────────────────────────────────────┤
  │ quality_filter                │ change_pct 必须 ≤6% │ 把上面这些几乎全毙了                             │
  └───────────────────────────────┴─────────────────────┴──────────────────────────────────────────────────┘

  排除原因统计:全部 120 只都含"涨幅>6%"。也就是说,上游拼命把强势票(涨停/大涨)排到 Compute Pool
  前列,下游过滤器又因为"涨幅>6%"把它们逐一枪毙。这不是数据问题,是逻辑设计冲突——两个环节对"什么是好票"的定义相反。

  修复方向(需你定夺):
  - 若策略核心是"抓未透支的中庸票"(2~6%),那 build_scan_pool 就不该把 limit_up 当最高优先级塞进来,QuickScore 的
  market_align 权重要重构;
  - 若策略要覆盖强势股,过滤器的硬上限 6% 就要放宽或改成软扣分(实际上 extract_risk_raw
  已经在做涨幅软扣分了,与硬过滤重复)。

  我倾向后者:去掉 quality_filter 里的涨幅/换手硬阈值,全部交给已有的 percentile 打分 + risk_penalty 软处理。硬阈值 +
  软扣分并存,是当前系统最大的设计冗余。

  🟠 三、质量过滤是"硬删除",没有兜底

  quality_filter 直接把不合格票丢进 filtered、不参与打分,一旦市场当天整体偏离阈值区间(如普涨或普跌日),就会像 7-01
  那样全军覆没,系统当天零输出。一个尾盘选股系统在活跃行情里反而选不出票,可用性上是不可接受的。

  建议:改成"打分后按分数排序取 Top N",而不是"先删除再打分"。或至少保留一个
  fallback:若过滤后为空,自动降级用未过滤池打分并标注告警。

  🟠 四、percentile 打分的固有缺陷:永远"矬子里拔将军"

  percentile_rank 把每一维强制拉成 0~100 均匀分布(score_overnight.py:64)。这带来一个策略隐患:

  - 无论当天市场多差,总会有票排到高分位。哪怕全池资金都在净流出,净流出最少的那只也拿到 capital 高分。
  - 系统没有绝对质量地板——分数是相对的,A 档不代表"好",只代表"这批里相对最好"。

  对隔夜策略这是危险的:弱势日里它照样会给出 A
  档买入信号。建议在最终分上叠加一个绝对门槛(如主力必须真净流入、trend_quality 原始值不能太低),percentile
  只用于排序、不单独决定入池。

  🟡 五、权重版本混乱,注释与实现脱节

  - WEIGHTS_V1_2 实际是 9 维(加了 intensity/conviction/consistency/trend_quality),但文件顶部 docstring 和子 skill
  SKILL.md 里写的还是旧的 5 维公式(Theme 30% / Capital 25%...)。
  - 主 SKILL 和 intraday-strategy SKILL.md 展示给用户/LLM 的评分维度表是过时的 5 维,与真正跑的 9 维对不上。LLM 写
  ReasoningTrace 时会依据错误的权重解释。

  修复:把 SKILL.md 里的评分维度表更新为实际的 V1.2 九维权重。

  🟡 六、theme_ranking 的"持续性"维度是假的

  compute_theme_ranking.py:97 里,Continuation(10%)恒等于常数 10:

  s["heat"] = bn*20 + ln*30 + cn*25 + mn*15 + 10   # 最后这个10是写死的

  markdown 输出里也直接印 10.0。所谓"5 维热度"实际只有 4 维在起作用,"持续性"从未被计算(需要昨日数据对比,V1
  没接)。建议:要么真正实现(接昨日 theme 数据),要么诚实地从公式和文档里去掉,别让它冒充一个维度。

  🟡 七、north_bound 数据源已失效

  7-01 那次 north_bound.json = {"error": "fetch failed"}。北向资金实时额度自 2024-08
  已停止披露,这个接口大概率永久失效。market_state
  里"资金方向/北向"会长期显示"数据缺失"。建议移除或替换为主力资金/两融等仍可得的口径。

  🟢 八、值得肯定的部分

  - 三层架构(Compute→Perception→Reasoning)干净:数字全由 Python 产出、LLM 不造数,这是正确的设计,避免了 LLM 幻觉编数据。
  - score_trace / confidence 机制好:每只票都留了五维贡献值和置信度(数据完整性+分数稳定性),可解释性强,也为 V2
  回测校准留了接口。
  - log 缩放、gaussian 甜点区、资金四档一致性(consistency) 这些细节都是有金融含义的合理设计。
  - 板块排除、去重、缓存 工程处理到位。
